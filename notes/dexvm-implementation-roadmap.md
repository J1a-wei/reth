# DexVM 实施路线图

## 项目目标

基于 Reth 构建一个以 DexVM 为核心的高性能去中心化交易所节点：
- **主执行引擎**: DexVM 处理所有交易业务逻辑
- **兼容保留**: EVM 预留但暂不启用，保持未来扩展性
- **初期部署**: 单节点模式，跳过共识层
- **性能目标**: 订单撮合 TPS > 200,000

---

## 阶段一：基础架构搭建（MVP）

### 1.1 DexVM 核心引擎
**目标**: 实现一个可独立运行的最小化 DexVM

**关键模块**:
```
crates/dexvm/
├── core/           # VM 核心执行引擎
├── state/          # DexVM 专用状态管理
├── instructions/   # DexVM 指令集
└── primitives/     # 基础数据类型（订单、账户等）
```

**核心功能**:
- [x] 指令集设计（下单、撤单、查询等）
- [ ] 内存高效的订单簿数据结构
- [ ] 状态存储接口（账户余额、持仓等）
- [ ] Gas 计费机制（可简化版本）

**里程碑验证**:
- 能够在单元测试中执行基本的下单/撮合交易
- 能够处理 10 万笔订单簿操作（Benchmark）

---

### 1.2 状态存储适配
**目标**: 将 DexVM 状态对接到 Reth 存储层

**集成点**:
```
crates/storage/
└── db/
    └── dexvm_tables.rs  # DexVM 专用数据表定义
```

**存储模式**:
```
DexVM 状态表：
- Accounts         (账户信息)
- Orders           (活跃订单)
- Positions        (持仓记录)
- TradeHistory     (成交历史，可选)
```

**关键决策**:
- 使用 Reth 现有的 MDBX 存储
- DexVM 表与 EVM 表完全隔离
- 考虑是否使用 Static Files 存储历史数据

**里程碑验证**:
- DexVM 状态能持久化到数据库
- 节点重启后状态完整恢复

---

### 1.3 交易处理管道
**目标**: 替换 Reth 的 EVM 执行器为 DexVM 执行器

**修改模块**:
```
crates/evm/          # 不修改，保留作为参考
crates/dexvm-evm/    # 新建：DexVM 执行器（模仿 EthEvmConfig）
```

**实现路径**:
1. 创建 `DexVmConfig` 实现 `ConfigureEvm` trait
2. 创建 `DexBlockExecutor` 处理区块中的 DexVM 交易
3. 定义 DexVM 交易格式（与 EVM Transaction 平行）

**交易格式设计**:
```rust
pub struct DexTransaction {
    pub sender: Address,
    pub instruction: DexInstruction,  // 下单/撤单等
    pub nonce: u64,
    pub signature: Signature,
}

pub enum DexInstruction {
    PlaceOrder { pair: TradingPair, price: U256, amount: U256, side: OrderSide },
    CancelOrder { order_id: OrderId },
    Withdraw { asset: Address, amount: U256 },
}
```

**里程碑验证**:
- 能接收并执行 DexVM 格式的交易
- 区块执行后状态正确更新

---

### 1.4 单节点出块器
**目标**: 实现一个简单的出块机制，跳过共识

**实现方案**:
```
crates/consensus/
└── single-node/     # 新建：单节点共识（无实际共识）
    └── producer.rs  # 定时打包交易到区块
```

**核心逻辑**:
- 固定时间间隔（如每 1 秒）打包一个区块
- 从交易池取出所有待处理交易
- 按 nonce 顺序执行 DexVM 交易
- 计算状态根并提交区块

**简化点**:
- 跳过 PoW/PoS 验证
- 单一出块者（无需拜占庭容错）
- 暂时不处理分叉

**里程碑验证**:
- 节点能自动打包并执行区块
- 通过 RPC 能查询最新区块高度和交易

## 阶段二：网络与 RPC 接口

### 2.1 DexVM RPC 接口
**目标**: 提供查询和发送交易的 API

**新增端点**:
```
POST /dex_sendTransaction      # 提交 DexVM 交易
POST /dex_getOrderBook         # 查询订单簿
POST /dex_getPosition          # 查询用户持仓
POST /dex_getTrade             # 查询成交记录
POST /dex_getBalance           # 查询账户余额
```

**兼容保留** (暂不实现):
```
POST /eth_sendRawTransaction   # 预留 EVM 交易接口
POST /eth_call                 # 预留 EVM 调用接口
```

**实现模块**:
```
crates/rpc/
└── rpc-eth-types/
    └── dexvm/      # DexVM RPC 类型定义
└── rpc-eth-api/
    └── dexvm.rs    # DexVM RPC trait 定义
└── rpc/
    └── dex.rs      # DexVM RPC 实现
```

**里程碑验证**:
- 能通过 RPC 发送交易并查询结果
- 订单簿查询返回正确的深度数据

---

### 2.2 交易池定制化
**目标**: 修改 Reth 交易池以支持 DexVM 交易

**修改模块**:
```
crates/transaction-pool/
└── pool/
    └── dexvm.rs    # DexVM 交易池扩展
```

**关键适配**:
- DexVM 交易的有效性验证（余额检查、nonce 检查）
- 订单优先级排序（价格优先、时间优先）
- 交易池大小和淘汰策略

**差异点**:
- 取消订单可能需要立即处理（不等下一区块）
- 同一用户多笔订单的处理策略

**里程碑验证**:
- 交易池能正确排序和管理 DexVM 交易
- 高负载下交易池不会溢出或阻塞

---

### 2.3 P2P 网络同步（可选）
**目标**: 允许多个观察节点同步数据

**核心功能**:
- 区块广播和同步
- 交易池广播（Gossip）
- 状态快照同步（可选）

**简化方案**:
- 初期只有一个生产节点，其他节点为只读
- 复用 Reth 现有的区块同步机制

**里程碑验证**:
- 观察节点能从生产节点同步完整区块链
- 新交易能广播到所有节点

## 阶段三：性能优化

### 3.1 订单簿引擎优化
**目标**: 达到 20 万 TPS 撮合性能

**优化方向**:
1. **数据结构**:
   - 使用 Red-Black Tree 或 B-Tree 替代 HashMap
   - 分层订单簿（限价单独立管理）
   - 内存对齐和缓存友好布局

2. **并行撮合**:
   - 不同交易对并行处理
   - 使用 Rayon 进行批量订单处理

3. **零拷贝序列化**:
   - 订单数据使用 `rkyv` 实现零拷贝反序列化
   - 减少内存分配

**Benchmark 指标**:
```
cargo bench --bench orderbook
目标: 单交易对撮合 > 200,000 ops/sec
```

---

### 3.2 状态存储优化
**目标**: 减少磁盘 I/O，提高状态读写性能

**优化策略**:
1. **缓存层**:
   - 热点账户缓存（LRU）
   - 活跃订单内存索引
   - 减少 MDBX 读操作

2. **批量写入**:
   - 区块执行结束后一次性提交状态
   - 使用 MDBX 事务优化

3. **静态文件**:
   - 成交历史和历史订单移至 Static Files
   - 只在 MDBX 保存活跃状态

**性能目标**:
- 区块执行时间 < 50ms（10 万笔交易）
- 状态提交时间 < 20ms

---

### 3.3 内存管理优化
**目标**: 降低内存占用，支持长时间运行

**优化点**:
1. **对象池**:
   - 订单对象复用（避免频繁分配）
   - 交易对象池化

2. **内存限制**:
   - 订单簿设置最大深度限制
   - 交易池大小限制

3. **垃圾回收**:
   - 定期清理已撮合/取消的订单
   - 历史数据归档

**监控指标**:
- 常驻内存 < 4GB（100 万活跃订单）
- 内存增长率 < 10MB/小时

---

### 3.4 网络优化
**目标**: 减少网络延迟和带宽占用

**优化策略**:
1. **压缩**:
   - 区块传输使用 Snappy 压缩
   - 订单簿快照增量更新

2. **批处理**:
   - 合并多笔小交易广播
   - 减少网络往返次数

3. **选择性同步**:
   - 轻节点只同步订单簿，不同步历史
   - 按需拉取历史数据

**性能目标**:
- 区块传播延迟 < 100ms（局域网）
- 带宽占用 < 10MB/s（每秒 1000 笔交易）

---

## 阶段四：EVM 集成（未来扩展）

### 4.1 双 VM 架构
**目标**: 启用 EVM，允许智能合约调用 DexVM

**实现方案**:
1. **Precompiled Contracts**:
   - `0x8000`: PlaceOrder
   - `0x8001`: CancelOrder
   - `0x8002`: QueryOrderBook

2. **状态共享**:
   - EVM 和 DexVM 共享账户余额
   - 原子性操作保证两边状态一致

3. **区块执行流程**:
   ```
   交易 -> 是 EVM 交易?
         -> 是: EVM 执行（可调用 DexVM Precompiles）
         -> 否: DexVM 执行
   ```

**里程碑验证**:
- ERC20 合约能调用 DexVM 下单
- 状态在两个 VM 间正确同步

---

### 4.2 兼容性测试
**目标**: 确保能运行标准 EVM 合约

**测试用例**:
- Uniswap V2/V3 部署和交易
- ERC20/ERC721 基础功能
- 与 DexVM 交互的复杂场景

## 技术决策记录

### 为什么先不启用 EVM？
1. **复杂度降低**: 避免双 VM 状态同步的复杂性
2. **性能优先**: DexVM 专注于订单撮合优化
3. **迭代灵活**: 先验证 DexVM 可行性，再考虑兼容

### 为什么单节点？
1. **快速验证**: 跳过共识协议开发
2. **性能测试**: 单节点可测最大 TPS
3. **渐进式**: 后期再引入共识层

### 为什么基于 Reth？
1. **模块化**: Reth 的 crate 结构便于替换组件
2. **高性能**: 存储和网络层已优化
3. **生态**: Rust 生态丰富（如 tokio, rayon）

## 风险与缓解

### 风险 1: DexVM 性能达不到预期
**缓解**:
- 阶段一结束立即进行 Benchmark
- 参考 Dolomite 等高性能 DEX 实现
- 必要时引入硬件加速（FPGA）

### 风险 2: Reth API 变动
**缓解**:
- 锁定 Reth 版本（如 v1.1.x）
- 关注 Reth changelog
- 模块边界清晰，减少耦合

### 风险 3: 状态膨胀
**缓解**:
- 订单簿限制最大深度
- 历史数据定期归档
- 使用 Static Files 分离冷热数据
